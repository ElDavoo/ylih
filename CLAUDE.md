# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An Android app (Kotlin, Compose, Room) that records how long each pair of headphones stays
connected, forever and locally, so lifetime hours per *physical pair* can be trusted years later.
`README.md` is the product-level description and is accurate — read it for the two tracking modes,
the accuracy rules and the flavor split before changing anything in those areas.

## Commands

The nix dev shell pins the exact JDK 21, Gradle 9 and Android SDK (platform `android-37.0`,
build-tools `37.0.0`):

```sh
nix develop            # or: direnv allow
```

Every Gradle task is flavor-qualified — there is no plain `assembleDebug`:

```sh
./gradlew assembleClassicDebug          # sideload build
./gradlew assemblePlayDebug             # store build
./gradlew installClassicDebug
./gradlew bundlePlayRelease             # Play Console AAB

# what CI runs, per flavor (matrix over classic/play)
./gradlew lintClassicReleaseTest createClassicReleaseTestUnitTestCoverageReport \
          assembleClassicDebug assembleClassicRelease

# a single test class or method
./gradlew testClassicReleaseTestUnitTest --tests '*SessionRepositoryTest'
./gradlew testClassicReleaseTestUnitTest --tests '*SessionRepositoryTest.a reconcile racing*'

# tests + JaCoCo report, then the same summary CI prints
./gradlew createClassicReleaseTestUnitTestCoverageReport
python3 .github/scripts/coverage-summary.py \
    app/build/reports/coverage/test/classic/releaseTest/report.xml classic
```

Debug builds carry `applicationIdSuffix = ".debug"`, so a debug and a release install coexist.

### Lint is a hard gate

`checkAllWarnings`, `warningsAsErrors` and `abortOnError` are all on, and `checkTestSources`
extends that to `src/test` and `src/androidTest`. Both belong to the `releaseTest` build type, so
`lint<Flavor>ReleaseTest` sees them — `lint<Flavor>Debug` still runs but has no test sources to
check. There is no baseline file: a baseline hides a finding instead of deciding about it. A
warning — including checks lint ships disabled — fails the build like an error.

The only two ways to land a finding are to fix it or turn the check off in `app/lint.xml` **with
a reason**. The checks off cannot hold here: `NewerVersionAvailable`/`GradleDependency` (they hit
the network, and versions are pinned on purpose), `DuplicateStrings` (77 translations of ~150
strings collide legitimately), `ConvertToWebp` *scoped to `res/drawable-nodpi`*, where the widget
previews are generated by a tool that writes only PNG, and `NewApi`/`InlinedApi` *scoped to
`src/test`* only, because Robolectric runs against the compile SDK rather than the minSdk 26
floor those checks enforce.

One consequence: a few members are `internal` rather than `private` purely so a nested class can
reach them without a synthetic accessor, with a comment saying so.

The Kotlin compiler is held to the same standard: `allWarningsAsErrors` fails the build on a
deprecation. The usual trigger is a Dependabot bump, and failing that PR is intended. Tests use
`androidx.compose.ui.test.junit4.v2.createComposeRule` for the same reason; its v2 rule dispatches
with `StandardTestDispatcher` rather than `UnconfinedTestDispatcher`, and the Roborazzi listing
captures were re-recorded and eyeballed against before the switch landed.

### Coverage

`enableUnitTestCoverage = true` on the `releaseTest` build type (see Testing) gives AGP a
`create<Variant>UnitTestCoverageReport` task; the report lands in
`app/build/reports/coverage/test/<flavor>/releaseTest/` and CI uploads it and prints the summary
table into the job summary.

**It is a gate, not just a report.** CI passes `--min-instruction=95 --min-line=98
--min-branch=70` and fails below any, printing the miss budget rather than the percentage. Line
sat at 99 until minSdk 26 made it uncollectable: on `classic`, `Distribution.HAS_SPECIAL_USE_FGS`
is compile-time true, so `TrackingController.detailedTrackingSupported()` short-circuits before
its Bluetooth-permission check, making `SettingsScreen`'s "detailed tracking unavailable" notice
unreachable — that path exists only for `play`, where API 34+ needs the permission since the
flavor declares no `specialUse` foreground-service type. Below API 26 an unfixed-service install
used to reach the same lines another way; raising the floor deleted that route, so this is dead
code on one flavor, not a testing gap. The shared floor costs the flavor that didn't lose lines:
`play` runs at 99.1 but is held only to 98, so a real regression there down to that line would
pass unnoticed.

Branch is gated looser — suite at 77.0, floor 70 — because the counter moves when a composable
gains a parameter rather than when testing gets worse (see below), so a tighter floor would fail
ordinary UI work as a regression. 70 leaves ~80 missed branches of headroom, enough that a breach
means something real. Method and class are ungated: at ~95% they are six classes from a 90 floor,
close enough that ordinary work would trip them.

`testOptions.unitTests.all` sets `isIncludeNoLocationClasses`: Robolectric's sandbox classloader
gives tested classes no code-source location, so JaCoCo drops them without that setting — the
report would read ~2%, only `stats/Stats.kt` (plain JVM tests) surviving while every
Robolectric-covered class reports zero. Check this setting first if coverage ever collapses.

`coverage-summary.py` reports the number over code this repo actually wrote. The report also
holds Room's KSP output (`*Dao_Impl`, ~a fifth of instructions) and stdlib/coroutines sources the
compiler inlines and attributes to our packages — `SafeCollector.common.kt`, `Emitters.kt`,
`LazyDsl.kt`, `Comparisons.kt` — nobody here can test those. Rule: a class counts if its source
file exists under `app/src`. The excluded total prints underneath rather than vanishing; the
report on disk stays untouched, since AGP's `JacocoReportTask` has no exclusion setting.

Two parts of the gap aren't worth chasing: branch coverage sits in the seventies because the
Compose compiler emits a `$changed`/default-argument bitmask branch per parameter that no test
drives (Compose-heavy files hold ~two thirds of missed branches); and a handful of lines are
unreachable by construction — the closing brace of a `collect` on a channel that never closes, and
`JsonBackup`'s `$default` constructor bridges, reachable only by a Kotlin caller omitting
arguments.

Neither flavor's report is the whole picture: `Distribution` constants are compile-time, so the
`HAS_SPECIAL_USE_FGS` branch reads uncovered on one flavor and covered on the other; CI runs both.
At minSdk 26 there is no build that cannot start the foreground service on its own (reachable
without the split at the old API 23 floor, but the floor moved past it) — the surviving,
flavor-gated route is `play` on Android 14+ with `BLUETOOTH_CONNECT` denied, the one place
detailed tracking is still refused. Prefer a non-split path where one exists; here it doesn't.
`TrackingControllerTest`, `SettingsScreenTest`, `YlihViewModelTest` and `DistributionTest` assert
`Distribution.HAS_SPECIAL_USE_FGS` or branch on it rather than skipping on the flavor that can't
reach the denied state — a skipped test reads as coverage while asserting nothing, so both
flavors assert every run.

## Architecture

### Everything writes through one funnel

`data/SessionRepository.kt` is the only place that mutates session state. Four independent
sources race into it — the manifest Bluetooth receiver, the foreground service, the heartbeat
worker and the UI — so every method takes a `Mutex` and runs inside a Room transaction, and
operations are idempotent by construction:

- a pair can never hold two open sessions (`openSession` heartbeats an existing one instead);
- closing an already-closed session is a no-op (the SQL carries `AND disconnectedAt IS NULL`);
- an open session older than `STALE_SESSION_MS` is split, not stretched, on the next connect;
- `reconcile` never counts across a boot, and `RECONNECT_GRACE_MS` stops it resurrecting a
  session a just-received disconnect closed.

These invariants are why the app exists.
`app/src/test/java/it/eldavo/ylih/data/SessionRepositoryTest.kt` pins them; touching this file
means that test is the contract.

### Who calls what

`tracking/TrackingController.kt` is the policy layer: it decides whether the foreground service
runs, whether the WorkManager heartbeat is scheduled, and repairs the database against reality.
`syncWithSystem()` is the single "make everything consistent again" entry point, safe to call as
often as you like. Invoked from `BootReceiver`, `MainActivity.onStart`, `HeartbeatWorker`,
`TrackingService.onCreate` and after a permission result.

- **Bluetooth-only (default)** — `BtConnectionReceiver`, a manifest receiver on ACL connect/
  disconnect. Nothing of the app is resident. A 15-minute `HeartbeatWorker` is scheduled *only*
  while a session is open, to bound the damage of a missed disconnect.
- **Detailed tracking (opt-in)** — `TrackingService`, a foreground service. It exists because
  wired plug events are only delivered to a live process; while up it also runs `PlaybackWatcher`
  and heartbeats every minute.

- **Battery, for charge cycles** — `BtBatteryReceiver`, a second manifest receiver. See below.

`data/AppContainer.kt` is a hand-rolled container reached via `(context.applicationContext as
YlihApp).container`. `YlihApp.onCreate` does almost no work, since it runs on every
broadcast-woken process start. Its one exception, `Notifications.ensureChannelAtStartup`, is
load-bearing: created on the line above `TrackingService`'s `startForeground`, the channel used to
silently fail to appear when the notification permission was denied, making `startForeground`
throw. The service catches that and stops itself, so detailed tracking died the moment it was
switched on, every retry repeating the same two calls in the same order. Creating the channel at
process start fixes it. `startForegroundCompat` must stay free of an `areNotificationsEnabled()`
check — the service must run and appear in the foreground-service manager whether or not its
notification may be drawn. `Clock` is a `fun interface` injected through the container so
time-sensitive logic is testable.

### Data model

`devices` (an identity as Android reports it) → `pairs` (one physical pair, the lifetime unit,
with `generation`) → `sessions` → `battery_samples`. Retiring a pair freezes its totals; the next
connection of the same device opens generation + 1 — also how wired headphones work at all, since
Android can't tell two wired pairs apart.

Two gotchas in `data/Daos.kt`: `observeSummaries()` and `observeSummary(pairId)` are the same
large aggregate query duplicated with a `WHERE` clause — change both. And `PairSummary.closedMs`
counts finished sessions only; live totals are `closedMs + (now - openSince)`.

**Device identity** (`tracking/AudioDevices.kt`) is the other invariant: the two platform views of
one headset report different addresses — `AudioDeviceInfo.getAddress()` redacts the leading octets
while the ACL broadcast gives the full MAC — so keys use the last two octets, all both APIs
disclose. Getting this wrong splits one pair's hours across two rows; `AudioDevicesTest` pins the
observed addresses.

### Charge cycles

`ylih · lifetime` answers "how long did these last". Charge cycles answer "how long does a charge
last, and how has that changed" — the battery-degradation curve issue #30 asked for. A cycle is
**a hundred percentage points used**, however many part-charges that took.

**Both Bluetooth receivers must be `exported="true"`, found on a phone.** The Bluetooth stack is a
separate app (uid 1002); an implicit broadcast from it no longer resolves a non-exported component
of ours — AMS drops it in `SaferIntentUtils.filterNonExportedComponents` *before* the
`BroadcastRecord` exists, so it doesn't even show as a skipped receiver in `dumpsys activity
broadcasts`. Measured on a Mi 10T on Android 16: with `exported="false"`, `BtConnectionReceiver`
saw nothing across five Bluetooth off/on cycles while another app's exported receiver logged
every one; flipping the attribute alone made both fire on the next cycle. That attribute is the
whole of Bluetooth-only tracking, so this was a live shipped bug, not only a charge-cycles
concern. Exporting costs nothing, since these are protected broadcasts.

#34 reverted the connection receiver to `"false"`, reading #31's A/B as confounded by the stopped
state — wrongly. Re-measuring on Android 17 settled it by reading the *receiver lists* out of
`dumpsys activity broadcasts` instead of inferring from app state. Toggling Bluetooth forces a
real reconnect, and the history names every receiver each broadcast resolved to, its `exported`
flag, and DELIVERED vs SKIPPED:

- Shipped build (connection non-exported, battery exported): one broadcast reached
  `BtBatteryReceiver` and, same process, same second, never listed `BtConnectionReceiver` — not
  skipped with a reason, never a candidate, exactly as `filterNonExportedComponents` predicts.
- With the two flags inverted, the verdicts inverted with them.

#33's evidence had another explanation: with detailed tracking on,
`TrackingService.syncWithSystem()` reconciles against the `AudioManager` list every minute and
opens the exact open session and scheduled `HeartbeatWorker` taken as proof the receiver fired —
watched happening while the receiver received nothing. That's why the bug survived a release: the
mode most people leave on hides it.

Two re-check traps: **`am broadcast` can't test the attribute** — it sets
`FLAG_RECEIVER_FROM_SHELL`, and a shell broadcast reaches a non-exported receiver happily (cold-
started one here), proving the opposite of the real stack. And **the sender's uid is the whole
question**, not the identical flags/permission: system_server (uid 1000) is exempt, so
`BootReceiver` stays `exported="false"` and still gets `BOOT_COMPLETED` — 139 such deliveries
counted on this device in one sitting — while uid 1002 is not. `ReceiverExportTest` pins both
attributes against a third flip.

**The broadcast is `@SystemApi`, and that's fine — for reasons, not luck.** Android has no public
API for a headset's battery. `tracking/BatteryBroadcast.kt` writes
`android.bluetooth.device.action.BATTERY_LEVEL_CHANGED` and its extra; its KDoc records three
facts checked against AOSP that make depending on them safe:
`RemoteDevices.sendBatteryLevelChangedBroadcast` sends it with **`BLUETOOTH_CONNECT`** as receiver
permission (already held, not `BLUETOOTH_PRIVILEGED`); it carries
`FLAG_RECEIVER_INCLUDE_BACKGROUND`, the flag `BroadcastSkipPolicy.disallowBackgroundStart` reads,
reaching a manifest receiver in a non-running process exactly as the ACL broadcasts do (identical
delivery flags on both); and it's a `<protected-broadcast>`, so no other app can write a battery
level into the database. Not guaranteed: that a given headset produces one at all, so the feature
stays invisible until it does.

**Only drain we watched is counted.** A drop counts only between two readings inside *one
session* — why `battery_samples` is keyed on `sessionId` rather than `pairId`, a schema property
rather than a check someone can forget. Points drained and listening credited then cover the same
stretches of time, so their ratio means something; counting a drop across a gap would break that
twice — no listening to attach to it, and a headset charged partway through the gap reports a
level that makes the drain look smaller than it was, with nothing to say so. `stats/Charge.kt` is
the whole calculation, pure and Room-free like `Stats.kt`, so `ChargeTest` is a plain JVM test; it
apportions playback across a segment with the same even spread `Stats.dailyMs` uses across
midnight, and drops a session that never measured playback from **both** sides of the ratio, as
`Stats.counted` does.

**The first reading of a session arrives before the session does.** Measured on the same phone:
ACL_CONNECTED at 08:20:52.721, battery broadcast at 08:20:53.131, `BtConnectionReceiver`'s own row
at 08:20:53.199 — 68 ms too late, so the reading was dropped. The two receivers race by
construction, since the connect one reads the tracking mode before writing and both hand work to
the same scope. `recordBatteryLevel` returns whether it found an open session, and
`BtBatteryReceiver` retries once after two seconds. Many headsets report battery only at connect,
so without the retry those pairs record nothing. `SessionRepositoryTest` pins it through
`BtBatteryReceiver.recordWithRetry`, whose `settleMs` parameter exists for this — `runTest` makes
the delay virtual; the same test against the real two seconds was flaky under a loaded suite.

**Virtual time alone was not enough — read the second attempt before writing another test like
it.** Driving the retry by hand (advance a second, write the connect, advance past the settle)
looks deterministic and isn't: `runTest`'s runner advances the clock to whatever task is scheduled
next, unconditionally, whenever the test body parks on a non-test dispatcher, and every Room call
parks on Room's transaction executor. Land the `delay` inside one of those windows and the runner
fires the retry *before* the connect is written: both attempts find no session, nothing is
recorded, and the assertion reads `expected:<[70]> but was:<[]>`. That's how it failed #42's build
after hundreds of green runs; a 300 ms stall in that window reproduces it every time. What holds
instead: ordering the two by the repository's own mutex. Launched `UNDISPATCHED`, it holds the
mutex before `launch` returns, the connect queues behind it, and the retry — locking again only
after its delay — queues behind the connect; the clock is then free to run away since nothing
depends on it. Price: **nothing may suspend between the launch and the connect**, which is why
the test says so.

**The receiver announces nothing.** `BtBatteryReceiver` calls neither `onSessionsChanged` nor
`onFiguresChanged`: a reading changes no figure any widget shows, and the heartbeat bounds a
missed disconnect rather than follows the battery. Three refusals in
`SessionRepository.recordBatteryLevel` each earn their line: a level outside 0..100 (the stack
broadcasts -1 for "unknown" on *every* disconnect, at face value dropping the whole battery to
nothing), no open session, and an unchanged level (re-announced on reconnect; a zero-drain segment
mid-discharge if stored).

The UI is one section on the pair page and nowhere else, absent until `pointsDrained > 0`.
`ui/BarChart.kt`'s geometry was split into a keyless `drawBars` so `CycleBarChart` draws the same
bars against an ordinal axis; `drawDailyBars` and the widget's bitmap path go through it unchanged.

**Everything here is bounded except the readings themselves — three goes to get right.** Charge
cycles have no window (a thirty-day view can't ask what a charge bought when the pair was new), so
a decade of them is the case to design for; each below was measured, not guessed:

- **The read must not name `sessions`.** A Room flow observes every table its query mentions, and
  the heartbeat writes to `sessions` once a minute. Joined, reading 400,000 readings took 3.5 s and
  re-ran every minute the pair page was open. `BatterySampleEntity` carries a redundant `pairId`,
  making the same read a covering scan of `(pairId, at)` — 1.5 s, only when a reading lands. The
  same trap `observeRecentSessions` and `summarizeLifetime` exist to avoid.
- **The summary belongs off the main thread.** `Charge.summarize` is 173 ms over a million
  readings; it used to sit in a `remember` keyed on the minute clock, and is now
  `YlihViewModel.chargeSummary` on `Dispatchers.Default`, with sessions reduced to spans *before*
  `distinctUntilChanged` — a heartbeat moves nothing a span holds, so nothing recomputes.
- **The list and chart are capped.** Three thousand cycles is three thousand rows between the
  chart and the sessions below it, and three thousand sub-pixel bars redrawn every frame. Rows stop
  at `PAIR_CYCLE_ROWS`, keeping absolute numbering; the chart averages runs of cycles into at most
  `MAX_CYCLE_BARS` (`bucketedBars`) so the whole lifetime fits a screen width. Tiles above stay
  exact, since they are counted rather than drawn.

Loading the readings at all is still linear: they are the pair's whole history by design. At a
percent per step and a cycle a day that's ~36,500 rows a year, so a decade is a second or so on a
background thread when a reading lands. If that stops being acceptable, the answer is a rolled-up
`cycles` table, not a window.

### App functions, the agent surface

`agent/YlihAppFunctions.kt` is an abstract `AppFunctionService` from which
`androidx.appfunctions`'s KSP processor writes the concrete `YlihAppFunctionService` and a schema
XML into `assets/`. Android 17's app functions are the on-device MCP equivalent: an annotated
method becomes a tool an assistant can discover and call.

**Query-only, and it stays that way.** Nothing an agent calls reaches a write, so
`SessionRepository` — the funnel every other source goes through — isn't one of them. Figures come
from `widget/WidgetData.kt`'s `widgetDataFlow`: a widget is the same problem (blind to the UI,
needing only numbers), and that code is already windowed, Glance-free and pinned by
`WidgetDataTest`. A third query path would be a third place for figures to disagree;
`loadWidgetData` isn't the entry point, since it's `@VisibleForTesting` and lint says so.

**The KDoc is the API.** `isDescribedByKDoc = true` means the comment on each function and each
`@AppFunctionSerializable` property is literally what the agent reads, written for a caller who
can't see the code. It costs no translations — not a resource, English by construction, like
`res/xml/app_metadata.xml`'s `description`. The one user-visible string there, `displayDescription`,
is the settings row's own `@string/settings_agent_body`, so the switch's promise and the system's
match. On a serializable the KDoc must be **inline on each property**; class-level
`@param`/`@property` tags aren't extracted.

**`isEnabled = false` is the opt-in, a compile-time default.** Baked into the generated schema as
`<enabledByDefault>false</enabledByDefault>`, so the functions are genuinely absent from the OS
index rather than merely ignored. Shipped enabled, they'd be callable between install and first
opening settings; disabling at first run would race an agent that had already indexed the app.
`SettingsStore.setAgentAccess` writes the row *and* pushes the state through `AppFunctionManager
.setAppFunctionEnabled` in one place — the same reason `setLanguage` mirrors its value: the row is
the source of truth, the OS state a projection, and a projection only some callers update drifts.
Below Android 17 `pushAgentAccess` no-ops.

**The `<service>` is `android:enabled="@bool/enablePlatformAppFunctionService"`.** That boolean is
the library's own, false in `values` and true in `values-v36`. The generated service extends a
class that exists only on Android 17, so without it an older OS with the appfunctions *extension*
library would bind a class it can't load. `PackageManager` also needs `MATCH_DISABLED_COMPONENTS`
to see the component in a test.

**The schema is a java resource, not an Android asset.** KSP writes it to a path beginning
`assets/`, landing it under `assets/` in the packaged APK and in front of the platform's asset
manager on a device — but Robolectric's asset manager reads the merged `src/main/assets` tree,
which the file never passes through, so `YlihAppFunctionsTest` reads it off the classloader
instead. That test pins the surface: the functions can't be *called* from a unit test at all (the
service's superclass isn't in the framework the suite runs against), so it asserts everything the
OS reads before binding — the two ids, the KDoc-produced descriptions, `enabledByDefault`, the
`<service>` element and the app metadata.

`app/src/main/keepRules/app-functions.keep` holds the generated service to its own name, and
`.github/scripts/r8-keep-check.py` asserts it, for the reason `glance-widgets.keep` exists: the
manifest is the only thing naming it, and renamed it still installs while the OS never binds it.

### Stats and UI

`stats/Stats.kt` is pure functions over `Span` (start, optional end, optional playing ms),
deliberately decoupled from Room so the maths runs as a plain JVM test. Day bucketing uses
`ZoneId` arithmetic, not 24 h blocks, so DST days bucket correctly.

The UI is Compose with a single `YlihViewModel` (`ui/YlihViewModel.kt`) exposing `StateFlow`s and
a `Channel` of snackbar messages, and a three-tab `YlihNavHost`.

The stats screen's thirty-day chart is followed by the same window as a list, one row per day with
the figure the bar can only be a proportion of.

- **It has no section header of its own.** `stats_daily_hours_30` titles the chart *and* the rows
  under it — one section, and that Text carries `heading()` for the screen reader, as the
  `by pair` header below it does.
- **Only the leading run of empty days is dropped** (`dailyBreakdown`). A fortnight-old install
  would otherwise open on sixteen rows of nothing, reading as history that was lost; a zero
  between two listened-to days, or a zero today, is a real answer and stays.
- **"yesterday" is a resource; the weekday beside older rows is not.** `formatWeekday` asks CLDR
  through an `EEE` pattern, so no language needs it translated. `stats_yesterday` could have come
  from ICU's `RelativeDateTimeFormatter` the same way, but CLDR has no relative-day field for 22 of
  the locales here and hands back the English word for them — exactly what `check`'s untranslated
  rule catches. Those 22 are written out by hand instead; the other 223 values *are* CLDR's,
  harvested once rather than read at runtime.

**The three tabs are one destination, not three.** They are pages of a `HorizontalPager` under the
single `tabs` route, swipeable since pages lay out side by side and the screen follows the finger —
a NavHost swapping content on a click can't do that, at best offering a slide animation. Left in
the back stack is the pair page, a genuine push over whichever tab was showing, running
`ui/NavMotion.kt`'s spec in step with the app bar `AnimatedVisibility` reading its fade half:

- The pager state is hoisted above the `NavHost`, since tabs leave the composition while the pair
  page is open, and a state remembered down there would hand back the first tab on the way out.
- Back off a tab is written by hand (`BackHandler` → page 0). The back stack used to do it free,
  since every tab was navigated to with `popUpTo(start)` and sat over the headphones tab. Disabled
  on the pair page: the `NavHost` registers its handler after this one and wins, but only while it
  has something to pop.
- Nothing needs doing for RTL — a horizontal pager reverses itself, as the nav bar does.

That spec is one file rather than six lambdas' constants because the bar isn't a destination and
is faded by hand, so the two stay in step only by reading the same thing. Each transition is a
fade *and* scale on **one** 350 ms tween, and the pop mirrors the push — the page compresses back
the way it grew.

Alpha and scale share a spec because splitting them leaves a hole. The fade used to be a shortened
fade-out followed by a delayed fade-in, on the theory that two half-drawn pages read as mud;
instead it produced a stretch mid-animation with neither page drawn, reading as a blink rather
than a transition. Overlapped, the arriving page's alpha covers exactly what the leaving one gives
up — both drawn over the same Scaffold surface, so there's never a frame of bare background.

**A back gesture does not run `popExitTransition`, and has not since navigation-compose 2.10.** It
seeks `predictivePopEnterTransition`/`predictivePopExitTransition`, a second pair whose defaults
are `DefaultNavTransitions`' — `scaleOut(targetScale = 0.7f)` with no alpha at all, and a spring
`fadeIn` underneath. A NavHost naming only the first pair silently gets these, so the pair page
shrank under the finger and stayed fully opaque to the end — the report behind #38 and #40, both
missed because they rewrote the alpha on `popExit`, which the gesture had stopped reading. Ours
are the pop itself rather than a gesture-specific variant, since releasing the gesture commits it
by animating the *rest of the pop* from where the seek left off: anything the two disagree about
is a jump at the handover. The swipe edge is ignored — this is a zoom along the z axis and looks
the same from either edge.

`NavMotionTest` pins that every transition carries a fade as well as a scale, and that the
predictive pair is the pop pair; `YlihNavHostTest` drives a real gesture through
`OnBackPressedDispatcher.dispatchOnBackStarted` and asserts by geometry that the page held at 0.9
of the way through has scaled to *our* factor, not the library's — alpha isn't in the semantics
tree, but the scale riding beside it is, and 0.92 against 0.7 isn't a close call. It drives the
swipe by finding the one node with a horizontal scroll range, the tabs' own lists being vertical.

The bar stays fade-only: it must hold its height for the whole exit, which stops the list under
it jerking — a scale would give that back.

**A row of stat pills is one group, and pressing a figure moves the figures beside it.** `StatRow`
in `ui/Components.kt` copies Material 3 Expressive's `ButtonGroup`: the pressed pill widens by
taking width *from its neighbours*, so the row rearranges itself and its own edges never move. It is
the app's only reader of `MaterialTheme.motionScheme` and its only haptic. Five decisions there are
not defaults, and `Components.kt` carries the detail of each:

- **The row owns the press; the pill only reports it.** Scaling a pill under a `graphicsLayer` was
  the first attempt and grew it *over* its neighbours rather than out of them. So `StatTile` takes
  an `onPressed` and holds no state, and `StatRow` holds the index. A row of one has nothing to take
  from and does not move, as a `ButtonGroup` of one does not; every row today holds two or three.
- **A `Layout`, not a `Row` of animated weights.** A weight is a composition-phase argument, so
  animating one recomposes every pill on every frame of the spring; the measure block reads the
  `animateFloatAsState` values instead and only re-measures. `placeRelative` reverses the group in
  RTL, and the last pill absorbs the rounding so the pills and the 8dp gaps add up exactly and the
  right edge does not breathe.
- **A `pointerInput`, not a `clickable`.** `clickable` costs a button role and an activate action on
  every tile, so a screen reader would announce eight buttons on the stats screen that do nothing
  when double-tapped. `ComponentsTest` asserts the absent click action, so a rewrite fails there
  rather than in someone's ears.
- **The tick waits for a completed tap.** Both screens are `LazyColumn`s, so a scroll begun on a
  figure arrives as a press; on touch-down that buzzes every drag. `tryAwaitRelease` returns false
  once the scroll takes the gesture. Its test drives a real drag and asserts a *neighbour* narrowed
  before checking for silence, since a gesture that never reached the row is also even and quiet.
- **`PILL_PRESS_EXPANSION` is 0.10, against `ButtonGroupDefaults`' 0.15**, because a ButtonGroup's
  items are single-line labels that cannot wrap. These carry a figure over a label, and a two-pill
  row hands the whole expansion to one neighbour — enough, in some of the 77 languages, to wrap a
  label and jog the row's height for the length of a press. The spec is `fastSpatialSpec`: spatial
  springs are underdamped and overshoot, which reads as a squeeze, where the critically damped
  effects springs would only slide the edges over.

**Above 600dp the nav moves to the side and the content stops stretching.** At `targetSdk 37` the
platform ignores orientation, resizability and aspect-ratio restrictions on any display wider than
that, and the Android 16 opt-out is gone, so a tablet gets this layout whether or not anything was
done for it.

- The width question is asked once, via `currentWindowAdaptiveInfoV2()` and
  `WindowSizeClass.WIDTH_DP_MEDIUM_LOWER_BOUND` — the whole reason
  `androidx.compose.material3.adaptive:adaptive` is a dependency. It's the **V2** call
  deliberately: `currentWindowAdaptiveInfo()` is deprecated in 1.3.0, and `LocalConfiguration
  .current.screenWidthDp`, the obvious no-dependency answer, is deprecated too — both fail this
  build.
- The `WideNavigationRail` sits in a `Row` **beside** the `Scaffold`, not in a slot of it —
  `Scaffold` has no side slot, and a rail inside the content lambda would leave the Scaffold
  computing insets and bottom-bar padding for the full window. That's also why the Scaffold's
  `contentWindowInsets` drops the start side when the rail is up: `enableEdgeToEdge()` is on and
  the rail already consumed it. The rail and `ShortNavigationBar` share one `selectTab` and one
  `tabSelected`, since they're one control drawn twice.
- `ContentWidth` caps every screen at `CONTENT_MAX_WIDTH`, wrapped around the pager's page lambda
  and the `PAIR_ROUTE` composable — the two places all four screens flow through. The cap sits
  above every phone width, so it can't change the phone layout, and none of the four screens knows
  it exists.

`YlihNavHostTest` covers both branches by *geometry* rather than presence, since the rail and bar
draw the same three labels: one row (same top, increasing left) at default qualifiers, one column
(same left, increasing top) at `w840dp-h1024dp`. Two tests, so the `wide` branch isn't on the
coverage gate's miss budget.

**Every user-visible string is a resource.** `res/values/strings.xml` is the whole vocabulary, with
77 `res/values-<lang>/strings.xml` translations beside it; lint runs with `abortOnError = true` and
`MissingTranslation` is an error, so an English string added without translating into all 77
breaks the build. `res/resources.properties` names the unqualified folder's locale, which
`generateLocaleConfig` needs to emit `res/xml/locales_config`. Deliberate exceptions carry
`translatable="false"` (`app_name`, `value_none`). House style is **lowercase throughout** —
`action_cancel` carries `tools:ignore="ButtonCase"` and the Norwegian `welcome_privacy` carries
`tools:ignore="Typos"`, since lint would otherwise insist on "Cancel" and "Internett".

Since lint is a hard gate, `UnusedResources` is one too: a string added before the UI that reads
it fails the build until something uses it. A `@string/` reference from the manifest or a resource
XML counts as a use, which is the only thing keeping the widget picker labels legal.

Two consequences: `DeviceKind.displayName()` is `@Composable` because it resolves a resource, and
`ButtonGroupScope` is *not* a composable scope, so labels for it must be hoisted out with
`stringResource` before the `ButtonGroup` call.

### Home-screen widgets

Three Glance widgets under `widget/`: `ylih · lifetime` (hours per pair, connected pair first),
`ylih · activity` (the grand total plus today / 7 d / 30 d) and `ylih · 30 days` (the stats
screen's bar chart). Glance is pinned at **1.1.1 stable** — two years older than everything around
it, since 1.2.0-rc01 and the 1.3.0 alphas are the only newer releases and neither has shipped. If a
Kotlin or Compose bump ever makes 1.1.1 fail `allWarningsAsErrors`, moving to `1.2.0-rc01` is the
intended answer rather than pinning the compiler back.

- **`widget/WidgetData.kt` holds everything but the drawing.** A rendered widget only exists
  inside a launcher, so figures are assembled Glance-free and tested like `Stats.kt`
  (`WidgetDataTest`). `SessionDao.since()` is the one added query — windowed, since a refresh must
  not read a table that grows forever. `widgetDataFlow` is the entry point, `loadWidgetData` its
  first emission: figures must be observable, not a reading (see *Refreshes are pushed* below).
- **The live timer is a `Chronometer`, not repainted text.** A widget can't animate; the system
  ticks a `Chronometer` for free. It arrives through `AndroidRemoteViews`, invisible from outside,
  so `chronometerBase()` makes the arithmetic testable. `devices_connected_for` is the
  Chronometer's *own* format string, keeping the phrase grammatical in languages that put the
  duration first.
- **A widget's composed tree must not change shape when its data changes.** A launcher doesn't
  re-inflate an existing widget: `AppWidgetHostView` recycles the view and *reapplies* new
  `RemoteViews` onto it, and Glance gives `LifetimeContent` the same root layout id at any row
  count, so a reapply always happens. Reapplying a differently-shaped tree lands one view's action
  on another — observed as `FrameLayout doesn't have method: setMaxLines` — throwing part-way and
  leaving the launcher showing the half-updated view. A stale `Chronometer` is worst: the system
  keeps ticking it, showing an ended session counting up that no later push can dislodge. That's
  why `ConnectedFor` composes for *every* row, hiding itself when disconnected rather than being
  omitted. `WidgetChronometerTest` pins it by applying one composition and reapplying the next
  onto the same view — the only way to see this, since either composition alone looks correct.

  Row count is the other shape that moves; retiring or deleting a pair used to throw the same way,
  but only while rows were *stretching*, since a stretched list has no trailing spacer and thus
  exactly one child per row, with nothing to replace a lost one. Where losing a row turned
  stretching off, the spacer appeared as the row vanished, child count held, and the update
  survived by accident. The trailing spacer is now always emitted, weightless when rows stretch,
  so child count no longer depends on pair count. `WidgetReapplyTest` sweeps that across the
  provider's whole declared height range, both directions.
- **The chart is a bitmap.** Glance has no Canvas and hands out only equal weights, so
  proportional bars can't be expressed; `ChartWidget` rasterises `drawDailyBars`, the same
  geometry `ui/BarChart.kt` draws on the stats screen. Cost: a bitmap bakes its colours, so
  flipping dark mode leaves stale bars until the next update — as does everything outside Glance's
  API-31 dynamic tokens, why chrome colours are `@color/widget_*` in four folders (`values`,
  `-night`, `-v31`, `-night-v31`), resolved by the launcher at inflate time.
- **Refreshes are pushed, never polled — except once a day.** `updatePeriodMillis` is 0. Background
  writes reach widgets through `TrackingController.onDataChanged` (wired in `AppContainer`),
  foreground edits through `YlihViewModel.mutate`. A new write path means adding it to one of
  those two; `refreshWidgets` swallows its own failures on purpose, since a cosmetic redraw must
  never fail a session write.

  The exception is the one figure a write can't announce. `todayMs`, the two window totals and the
  chart's series bucket by *local midnight*, so they also move when the **date** does — and
  crossing midnight with nothing connected reaches neither push. `ylih · activity` went on showing
  yesterday's hours under "today" until the first connect of the new day; the app's own screens
  never had this, since they re-derive from `nowMinute` and a launcher has nothing that ticks.
  `widget/WidgetRollover.kt` is the daily wakeup closing it, kept deliberately small: armed only
  while a widget showing a dated figure is placed (asked of `AppWidgetManager`, not
  `GlanceAppWidgetManager`, whose provider map is empty until a widget has composed — on a fresh
  boot that would cancel the very schedule it means to keep), cancelled again when the last one
  goes. `LifetimeWidget` is excluded: lifetime hours and a `Chronometer` don't know what day it is.

  It is *periodic* work with `setNextScheduleTimeOverride`, not a chain of one-shots. One-shot
  work can't re-arm itself — enqueued under its own unique name from inside its own run, `KEEP`
  drops the request as a duplicate and `REPLACE` cancels that run halfway through. The override
  must be re-stated every run too, since WorkManager measures the next period from the *end* of
  the last one: however late a run is delivered is otherwise added to every day after, sliding a
  00:00 job into the afternoon over a few months. `UPDATE` re-times work in place without
  cancelling the caller; ordinary callers pass `KEEP`, since the service's tick reaches
  `refreshWidgets` once a minute and the schedule must not be rewritten each time.

  Three non-interchangeable doors reach that one callback: `onSessionOpened`/`onSessionClosed` are
  the broadcast receiver's; `onSessionsChanged` is the same bookkeeping without the service start,
  for `TrackingService`, which writes wired connects/disconnects itself — a plug event reaches no
  receiver or worker, so before this call existed widgets kept stale figures until something else
  redrew them. `onFiguresChanged` is the redraw alone, for the service's minute tick: it must not
  re-enqueue the heartbeat sixty times an hour, and accrued playback is a figure nothing else
  announces.

  **A push alone does nothing.** `updateAll` does not re-run `provideGlance`. Glance runs that once
  to *start a session* (a `SessionWorker` under WorkManager) keeping the composition alive ~45
  seconds; an `updateAll` inside that window only recomposes what's already there, since its
  `UpdateGlanceState` event re-reads the widget's own Glance state and nothing else. Figures loaded
  in `provideGlance` can't change mid-session, so every push in that window faithfully redrew
  numbers it already had — reading on the phone as updates going missing, not staleness: a connect
  changed the database, app and notification, pushed an accepted refresh, and left the home screen
  unchanged. With detailed tracking on it looked like a timer, since the service's minute tick
  outlasts 45 seconds: the tick was always the push finding no session, starting one, and reading
  the database again a minute late.

  **`widget/WidgetRefresh.kt`'s `YlihWidget` stops that returning**, as a base class rather than
  three corrected `provideGlance` bodies. `provideGlance` is `final` there, so a subclass writes
  only `Content`; everything `Content` gets — figures *and* localised context, since language can
  go stale too — arrives from the `widgetContentFlow` the composition is collecting. A live
  session's own observation delivers changes; when none runs, `refreshWidgets` starts one, both
  needed, neither enough. A new widget can't capture a snapshot since it never loads one, and
  `WidgetProvidersTest` reads the merged manifest rather than naming the three receivers, so a
  fourth widget can't arrive by another door. `sizeMode` is `final` on the same class for the same
  reason.

  No test reaches the session boundary itself: nothing outside Glance can start a session
  (`ContentReceiver`, which `provideContent` needs, is library-internal), and
  `runGlanceAppWidgetUnitTest` can't see a state change after the first composition — it
  re-snapshots the tree only on a `Recomposer` `Idle` *transition*, and the conflated `StateFlow`
  never reports Idle→Idle, so even a plain `mutableStateOf` looks frozen. `YlihWidget.provideGlance`
  is thus `widget/`'s one uncovered block. `WidgetDataTest` pins the reachable half: figures are a
  flow that keeps emitting, not a reading.

- **Every widget is `SizeMode.Exact`** (`final` on `YlihWidget`), and the layout arithmetic —
  `lifetimeRows`, `activityGrid`, `fits` — is Glance-free and unit-tested like `WidgetData`. Fixed
  `SizeMode.Responsive` buckets forced the providers' resize range to stay narrow: a size between
  two buckets draws the smaller layout and leaves a band of empty background, so every size the
  launcher allows needs a bucket. `WidgetProvidersTest` sweeps the whole declared range through the
  layout functions, keeping `res/xml/widget_*_info.xml` and the layout code from drifting apart.
  Widen a resize range and that sweep proves the new sizes draw something.

Every row's tap carries a distinct `ylih://widget/<pairId>` data URI. `PendingIntent`s are told
apart by action, data, type, component and categories and **never** by extras, so without it all
eight rows of a tall widget would open the same pair.

The live timer is the one thing Glance's node matchers can't see — it arrives inside an
`AndroidRemoteViews` and reads as an empty leaf, so `WidgetChronometerTest` composes to a
`RemoteViews`, inflates it and looks for the `Chronometer` itself — the suite's only assertion
reaching past Glance's own tree.

The picker previews in `res/drawable-nodpi/widget_preview_*.png` are **committed**, generated by
`WidgetPreviews` with Roborazzi and referenced from `res/xml/widget_*_info.xml`, so they must exist
in the tree for the build to compile. Nothing in CI regenerates or compares them: a widget redesign
leaves a stale picker picture until someone runs

```sh
./gradlew recordRoborazziClassicReleaseTest && git status
```

They're recorded at the size a launcher actually *places* the widget, not the `cells()` minimum
the provider declares, since that minimum is a resize floor and shows three rows crammed into two.

## Build-system constraints

These are easy to break and the failures are confusing:

- **There are two KSP processors**, Room's and `androidx.appfunctions`'s. Both inherit the same
  wiring generically — `android.disallowKotlinSourceSets=false` and the `lint`→`ksp` `dependsOn`
  at the bottom of `app/build.gradle.kts`, matching every `ksp*Kotlin` task — so adding the second
  needed no build change beyond the dependency. `androidx.appfunctions` is pinned by hand and
  **ignored in `.github/dependabot.yml`**, the same bargain `material3` gets: the line churns in
  ways that are code changes rather than version bumps (`@AppFunction` moved package between
  alpha10 and alpha11), so a grouped weekly PR is one merge or none.
- **AGP 9 compiles Kotlin itself.** The standalone `kotlin-android` plugin is absent on purpose,
  and AGP rejects it. The `kotlin` and `ksp` versions in `gradle/libs.versions.toml` must stay
  equal and aligned with the Kotlin Gradle plugin AGP bundles; KSP's release cadence pins Kotlin
  below the newest release.
- **`android.disallowKotlinSourceSets=false`** in `gradle.properties` is required, since KSP still
  registers Room's generated sources through `kotlin.sourceSets`.
- **The `lint`→`ksp` dependency wiring** at the bottom of `app/build.gradle.kts` works around AGP 9
  lint reading generated dirs without declaring a dependency; removing it makes lint race KSP and
  fail on a missing `*_Impl.kt`.
- **Version pins are duplicated in three files** — `gradle/libs.versions.toml`, `flake.nix` and
  `.github/workflows/*.yml` all name build-tools `37.0.0` / platform `37.0`. Change together. The
  F-Droid recipe (`metadata/it.eldavo.ylih.yml`) names no SDK version on purpose: its buildserver
  preinstalls nothing past 33 and relies on AGP downloading what `compileSdk` and
  `buildToolsVersion` ask for — see `docs/fdroid.md` §2.
- **Every download the build makes is pinned, and both pins are hand-maintained.**
  `gradle/wrapper/gradle-wrapper.properties` carries `distributionSha256Sum` for Gradle itself,
  and `gradle/verification-metadata.xml` carries a SHA-256 for all ~685 dependency artifacts.
  Without them the build runs whatever the network serves — the one unverified input a
  reproducible build cannot afford. F-Droid's review bot flags the first as `insecure-gradlew`.

  **Dependabot updates neither.** It bumps versions in `libs.versions.toml` and leaves the
  metadata alone, so every weekly gradle PR fails with "Dependency verification failed … checksums
  are missing" until regenerated — [dependabot-core#1996
  ](https://github.com/dependabot/feedback/issues/908) is the open upstream request.
  `.github/workflows/dependabot-verification-metadata.yml` closes it: on a Dependabot PR touching
  `libs.versions.toml` it regenerates the file and pushes it back onto the PR branch, so Android CI
  can judge the PR and `dependabot-auto-merge.yml` can merge unattended. The tradeoff any CI
  regeneration has: it records whatever was downloaded at that moment, moving trust from the
  checksum to whoever reviews the diff — for a Dependabot bump, the same person either way.

  Three load-bearing details. It pushes with `secrets.DEPENDABOT_PUSH_TOKEN`, which must be a
  GitHub App or user token stored as a **Dependabot** secret rather than an Actions one: a run
  triggered by Dependabot sees only that store, and a push made with `GITHUB_TOKEN` triggers no
  workflow runs, so the metadata commit would move the head SHA to one with no checks and
  auto-merge would wait forever. It gates on `github.actor == 'dependabot[bot]'`, which also stops
  it running twice, since the push arrives as a `synchronize` whose actor is the token's owner.
  And the build step is `continue-on-error`, since a bump that breaks compilation still resolved
  what it needed first — the metadata it wrote is correct and worth pushing, and CI on the new
  commit then reports the real failure instead of "checksums are missing".

  Regenerate by hand for anything Dependabot didn't raise — a manual version bump, or a Gradle
  upgrade — over the whole CI task set, not a subset: an unresolved configuration contributes no
  checksums, and `--refresh-dependencies` isn't optional, since an already-cached artifact isn't
  re-resolved and its checksum is silently left out. Both mistakes were made and caught here: the
  first pass missed the androidTest configurations, the second still missed five BOM and parent
  POMs that were cache-resident.

  **And clear `GRADLE_OPTS` first** — the trap this dev shell sets. `flake.nix` points
  `android.aapt2FromMavenOverride` at the SDK's own patched `aapt2`, since the one AGP fetches from
  Maven is dynamically linked and won't run on NixOS. A build under that override never resolves
  `com.android.tools.build:aapt2`, so the metadata written here is complete for this machine but
  short two artifacts everywhere else. The F-Droid buildserver found it one task in: `2 artifacts
  failed verification`, the `linux` jar and its POM. Nothing local can catch that, since every
  local build is under the override — the only proof is a run without it (the command below),
  which is also why the workflow above regenerates on a runner: a runner sets no override, so what
  it records is what an ordinary build needs.

  ```sh
  GRADLE_OPTS= ./gradlew --write-verification-metadata sha256 --refresh-dependencies \
      lintClassicReleaseTest createClassicReleaseTestUnitTestCoverageReport \
      testClassicDebugUnitTest assembleClassicDebug assembleClassicRelease \
      assembleClassicReleaseTestAndroidTest \
      lintPlayReleaseTest createPlayReleaseTestUnitTestCoverageReport \
      testPlayDebugUnitTest assemblePlayDebug assemblePlayRelease \
      assemblePlayReleaseTestAndroidTest
  # then prove it, since generation and verification are different code paths:
  GRADLE_OPTS= ./gradlew --refresh-dependencies assembleClassicRelease
  ```

  The wrapper is the one half Dependabot handles by itself. It bumps `distributionUrl` *and*
  `distributionSha256Sum` together — PR #14 moved Gradle 9.7.0 to 9.7.1 with the new sum written
  in — so nothing here has to. What it still can't do is the artifact metadata beside it, which is
  what the workflow above exists for; the two halves of a wrapper-plus-dependency bump land from
  different places and both must be right before the build starts. Gradle refuses to run rather
  than continuing quietly when the sum is stale — the behaviour worth having.

- **R8 runs on release builds** via AGP 9.3's `optimization { enable = true }`, turning on code
  *and* resource shrinking and supplying the platform keep rules, so there's no `proguardFiles`
  call and no `proguard-rules.pro`. Keep rules go in `app/src/main/keepRules/*.keep`; the app
  authors exactly one file there, `glance-widgets.keep`, holding the three `GlanceAppWidget`
  subclasses to their own names. Glance identifies a widget by its class's canonical name and
  persists that name per receiver, so when R8 merged the three (identical in shape, differing only
  in which composable they name), all three receivers recorded one provider and every widget on
  the home screen drew whichever had refreshed last. Every other rule comes from AGP's defaults or
  a library's consumer rules. Unit tests run on the JVM against unshrunk classes and never execute
  what R8 produced; two things cover that gap, both under Testing.

  `.github/scripts/r8-keep-check.py` is the cheap half: it reads the `mapping.txt` an
  `assemble<Variant>Release` writes and asserts R8 ran and that name-reached classes — the two
  workers above, whose names WorkManager persists in its own database — survived intact. No
  device needed, so CI runs it per flavor on every push:

  ```sh
  ./gradlew assembleClassicRelease
  python3 .github/scripts/r8-keep-check.py app/build/outputs/mapping/classicRelease
  ```

  `app/src/androidTest` is the expensive half: it installs the minified APK on an emulator and
  runs it — see Testing for what the two together do and don't prove.

## Room migrations

`exportSchema = true` with schemas committed under `app/schemas/`, and the database is built with
no fallback. Any entity change needs a `version` bump plus a real `Migration`, or existing installs
crash on open — and this app's entire premise is that history is never lost.

## Testing

Almost everything is a unit test run under Robolectric (`@Config(sdk = [...])`).
`MainActivityTest` is a startup smoke test that boots the Application, opens the real Room
database and drives `MainActivity` to RESUMED. Repository tests use an in-memory database with an
injected clock (`SessionRepository(db) { clockNow }`), so time is moved by assignment rather than
by sleeping.

**The unit test JVM asks for `maxHeapSize = "1g"`, not decoration.** Gradle's default is 512m, and
the suite outgrew that: all ~570 tests run in one JVM, each Robolectric test holding a simulated
framework and a parsed resource table, plus the widget tests' real bitmaps. Below the limit the
failure never names memory. Measured: 320m fails with an `OutOfMemoryError` attributed to whichever
test was running; 448m *passes* 570 of 571 but takes 9m14s instead of 2m45s — heap full rather than
exhausted, time spent collecting, with an arbitrary test timing out inside `runTest` as the one
casualty. A CI machine sized to 512m reports a single unrelated failure that reproduces nowhere and
moves every run.

**`src/androidTest` lives on the `releaseTest` build type**, i.e. `testBuildType`: R8 only runs
for a release build, so testing what R8 produced means pointing androidTest at a minified one.

`src/test` used to be dragged along with it — AGP creates unit tests only for `testBuildType`,
which is why every test task was `…ReleaseTest…`.
`android.onlyEnableUnitTestForTheTestedBuildType=false` in `gradle.properties` undoes that: each
build type now has its own unit test variant, and CI runs the suite twice, on `releaseTest` and
`debug`. Only `releaseTest` is instrumented for coverage, so
`create<Variant>ReleaseTestUnitTestCoverageReport` remains the single source of the gate's
numbers. Consequence: that flag hands `release` a unit test variant too, and `release` must never
carry `ui-test-manifest` — so `test<Flavor>ReleaseUnitTest` is explicitly disabled in
`app/build.gradle.kts` rather than left to fail on the first `./gradlew check`.

`testBuildType` itself reads `-Pylih.testBuildType`, defaulting to `releaseTest`. Passing `debug`
aims the same androidTest source set at an unminified build; CI runs both legs, and comparing
them is what separates "R8 broke it" from "it was always broken" without bisecting keep rules:

```sh
./gradlew -Pylih.testBuildType=debug connectedClassicDebugAndroidTest
```

`releaseTest` is `initWith(release)` — same shrinking, same signing — plus
`releaseTestImplementation(ui-test-manifest)`. That dependency is the whole reason it's a build
type of its own rather than plain `release`: `createAndroidComposeRule<ComponentActivity>` needs
the activity ui-test-manifest contributes to the merged manifest, and on `release` its absence
fails 197 unit tests with "Unable to resolve activity". Satisfying it there would mean shipping a
test activity to users.

`app/src/androidTest/MinifiedReleaseTest.kt` is the only place the shipped code executes: an
emulator in CI, covering what a name rather than a symbol reaches — Room's `_Impl` lookup,
WorkManager instantiating both workers from a stored class name, serialization's generated
descriptors, and the app starting at all. Its `-dontwarn` rules live in
`app/src/androidTest/keepRules/` and don't touch the shipped APK. Running it locally needs a
device and the four `ANDROID_SIGNING_*` variables, since an unsigned APK won't install:

```sh
./gradlew connectedClassicReleaseTestAndroidTest
```

`app/src/releaseTest/keepRules/instrumented-test.keep` holds what the app APK must keep for the
test APK to link against: AGP builds androidTest with `-keep class * {*;}` plus `-applymapping`,
packaging nothing the app already provides (no Kotlin runtime, not even `androidx.tracing`), so
anything R8 deleted resolves to nothing on a device, and anything R8 *reshaped* (a staticised
method, say) breaks the call site even where the class survived. It doesn't reach `release`.

The static counterpart is `.github/scripts/r8-keep-check.py`, which reads R8's mapping file and
needs no device. Between them: the script proves nothing was stripped or renamed on every push,
the emulator proves what survived still works.

The widgets are tested at both ends and not in between: `WidgetDataTest` on the figures, `WidgetsTest`
on what each size bucket renders via `runGlanceAppWidgetUnitTest`. That second one needs
`@GraphicsMode(NATIVE)` because the chart really rasterises — Robolectric's legacy graphics return
a null `Bitmap`, which surfaces as an NPE from inside Compose.

## Style

Comments in this codebase explain *why* — a platform quirk, a Play-review constraint, a race that
was actually observed — not what the code does. Match that: if a line needs a comment, the reason
is usually external to the code. Commit messages follow the same habit: a plain-language subject
line and a body explaining the reasoning and the evidence behind it.
